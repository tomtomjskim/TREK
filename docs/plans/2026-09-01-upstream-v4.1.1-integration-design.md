# TREK v4.1.1 Fork Integration Design

> 작성일: 2026-09-01
> 상태: 통합 착수 전 설계·감사 완료, 격리 통합만 조건부 GO
> 현재 runtime: 공식 `v3.4.1` 기반 포크 (`7a50356e`, image `trek:3.4.1-jsnetworkcorp-7a50356e`)
> 통합 후보: unsigned annotated tag `v4.1.1`, peeled target `33a33e7b1d113f0742ac609305cc549a4806d31b`
> 포크 기준: `6048db1374590402c4e982ba630dca31e43bb424`

## Decision

`v4.1.1` 통합은 가능하지만 자동·무충돌 업데이트가 아니다.

- **GO**: 현재 포크 `main`에서 분기한 격리 worktree의 `sync/upstream-v4.1.1`
  브랜치에서 exact tag target을 merge하고, v4 소유 모듈 위에 포크 계약을 테스트
  우선으로 다시 이식한다.
- **NO-GO**: 현재 포크 `main` 직접 merge, origin push, 포크 main 통합, 운영 Compose
  교체, production DB migration.
- `v4.1.1` 통합 gate가 모두 통과하기 전에는 현재 runtime/version 문서를 `4.1.1`로
  바꾸지 않는다.
- 공개 여행 장소 메모 개선은 legacy와 v4 양쪽에 이중 포팅하지 않고, 안정화된
  v4.1.1 통합 tree 위에서 별도 TDD 변경으로 수행한다.

Gate는 `full_gate_required`, rollback class는 `data_migration`이다. Production rollback은
writes를 다시 열기 전에 선택해야 하며, 동일 logical point의 DB/uploads/plugin state
snapshot과 pinned old image를 함께 복원하는 절차다. DB나 image 하나만 되돌리는 방식은
허용하지 않는다.

## Goals

1. 공식 `v4.1.1` ancestry와 신규 기능·보안 수정을 포크에 보존한다.
2. 포크의 DB namespace, packing privacy, Google 비용 상한, Vacay 데이터 안전성,
   지도/Fold/calendar UX, Android instance 자산을 누락 없이 재구성한다.
3. upstream에 동등 구현이 생긴 patch는 음성 회귀 테스트가 증명한 경우에만 퇴역한다.
4. data migration, immutable image, backup/restore와 공개 브라우저 증거가 연결된
   재현 가능한 release candidate를 만든다.
5. 낮은 모델 또는 낮은 추론 강도의 subagent도 파일 소유권과 검증 계약만으로 안전하게
   실행할 수 있는 문서·handoff 구조를 유지한다.

## Non-goals

- 이 설계 단계에서 실제 merge conflict를 해소하거나 애플리케이션 코드를 변경하지 않는다.
- TOM의 별도 요청 없이 origin/upstream에 push, PR, issue, Discord 게시를 하지 않는다.
- 운영 DB 원본, `.env`, token, signing key 또는 사용자 데이터를 검사·기록하지 않는다.
- v4 통합과 동시에 S3 storage reassignment, plugin data 이동 또는 인프라 재배치를 하지 않는다.
- 삭제된 `server/src/services/**` legacy service를 부활시키지 않는다.

## Options considered

### A. 모든 conflict에서 기존 fork 파일을 우선 선택

v4의 Nest 전환, auth default-deny, storage/provider 구조와 지도 수정이 사라질 수 있다.
특히 modify/delete된 legacy service를 되살려 이중 runtime을 만들 위험이 있어 기각한다.

### B. v4.1.1에서 새 branch를 만들고 fork commit 64개를 순서대로 cherry-pick

upstream ancestry는 단순하지만 patch-id 동등 커밋이 없고 파일 소유권이 대규모로
변경됐다. 오래된 구현 세부가 새 구조를 덮을 위험이 높고 포크 `main`의 release merge
정책에도 맞지 않아 기각한다.

### C. exact tag merge ancestry + upstream-first contract reconstruction — selected

`origin/main` 기반 격리 branch에서 `v4.1.1^{}`를 `--no-ff` merge한다. conflict 파일은
v4.1.1 구조를 baseline으로 해소하고, 포크 동작은 보존 매트릭스의 RED tests를 새 public
entry point로 이식한 뒤 최소 구현한다. merge ancestry와 포크 계약을 모두 추적할 수 있다.

## Target architecture

```text
origin/main (deployed 3.4.1 fork)
  -> isolated sync/upstream-v4.1.1
     -> exact v4.1.1 merge ancestry
        -> DB bridge + official migrations 176..200 + fork IDs
        -> upstream Nest/auth/privacy/storage baseline
        -> fork contract reconstruction by lane
        -> public shared place-note change
        -> full evidence + immutable image + restore rehearsal
           -> explicit TOM approval gates
              -> origin push/main integration
              -> separate production deployment
```

Conflict resolution order is mandatory:

1. DB and migration ownership
2. auth, permission and privacy
3. provider calls and durable cost limits
4. application behavior and UI
5. tests, docs and instance-only wiring

`ours`/`theirs`를 디렉터리 단위로 선택하지 않는다. 각 conflict는 보존 매트릭스 ID와
연결하고, 완료 조건은 conflict marker 제거가 아니라 해당 behavior test의 GREEN이다.

## DB and migration contract

공식 `server/src/db/migrations.ts`와 numeric `schema_version`은 upstream 소유다.
포크는 다음 기존 adapter를 보존한다.

- `server/src/db/forkMigrations.ts`
- `server/src/db/migrationRunner.ts`
- `fork_schema_migrations`
- stable IDs `jsnetworkcorp.google_api_usage.v1`,
  `jsnetworkcorp.packing_template_scope.v1`과 legacy collision bridge. 이 값은
  `FORK_MIGRATION_IDS` exported exact set의 단일 source로 정의하고, migration runner가
  각 ID를 한 번만 적용했음을 그 export에 직접 바인딩해 검증한다. 테스트에 문자열을
  다시 하드코딩해 비교하는 방식은 계약 증거로 인정하지 않는다.

Runtime order remains:

```text
exact legacy signature bridge
  -> upstream runMigrations (through schema 200)
  -> fork migrations by stable ID
  -> fork invariant assertions
```

`server/src/db/database.ts` conflict는 v4의 `readEnv`, SQLite durability pragma, rating
initialization을 유지하고 migration import/call seam만 `migrationRunner`로 연결한다.
v4에서 제거한 legacy `backfillFlightEndpoints`는 복원하지 않는다.

필수 rehearsal inputs:

| 입력                               | 기대 결과                                               |
| ---------------------------------- | ------------------------------------------------------- |
| fresh DB                           | official 200 + every current fork ID                    |
| stock official 171/172/173/175     | official 200 + fork IDs                                 |
| deployed fork 175 + fork IDs       | data preserved, official 200, same fork IDs once        |
| legacy fork marker 172/173         | exact signature bridge 후 official 200                  |
| official/fork migration rerun      | no data or marker drift                                 |
| schema commit before marker update | exact known state only resume                           |
| bridge/official/fork crash windows | committed work replay-safe, unknown partial fail-closed |
| unknown mixed signature            | startup abort; automatic guessing forbidden             |

Every rehearsal checks `PRAGMA quick_check`, `PRAGMA foreign_key_check`, schema 200, fork ID
set, and non-sensitive row-count/hash invariants for packing, Vacay, trips and provider ledgers.

Official migrations 176..200 include normalization, backfill and data modification. Notable
surfaces are Vacay models, feature flags, budget ticket/receipt extraction, invalid reservation
position deletion, Google/Unsplash key promotion, GB region reconciliation, file prefix
normalization, reservation ingest state and MCP token kind. A rollback after migration therefore
means the pinned old image **plus the checksum-bound same-logical-point DB/uploads/plugin snapshot**
while writes remain quiesced, not an image-only or DB-only switch.

## Fork preservation policy

Detailed behavior IDs, new module ownership and retirement signals live in
[`2026-09-01-upstream-v4.1.1-preservation-matrix.md`](2026-09-01-upstream-v4.1.1-preservation-matrix.md).
The governing rules are:

1. Security, privacy, destructive data safety and provider hard caps are preserved by default.
2. An upstream implementation retires a fork patch only after the fork's positive and negative
   tests pass against the new public entry point.
3. Legacy implementation files are never the contract. Tests and externally observable behavior are.
4. If v4 adds a broader feature but omits a fork safety invariant, keep the invariant in the v4 owner
   module rather than layering a parallel legacy service.
5. Instance-only Android/infra assets never enter an upstream contribution branch.

## Release and runtime configuration

The integration must audit names and validation without reading deployed values:

- `PLACES_API_KEY`, `PLACES_API_BASE`, `CARTO_API_KEY`
- `HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY`
- `TREK_DB_JOURNAL_MODE`, `TREK_DB_SYNCHRONOUS`
- `TREK_MANAGED=true` and `ENCRYPTION_KEY`
- storage seed-once `storage-config.json`
- every fork `TREK_GOOGLE_CAP_*` setting and enrichment flag name

S3 reassignment is a later rollout. The v4 code may be present, but the upgrade release keeps the
current storage assignment unless a separate backup/rollback plan is approved.

Storage/plugin rehearsal is release-blocking even when reassignment is not in scope. On a sanitized
candidate, record the seed-once transition and the effective (masked, non-secret) storage config,
then exercise representative object read/write/delete/restore through every configured local/S3/
mirror path. Create an application backup manifest containing DB snapshot identity, plugin rows,
blob/object keys and code/image checksum; verify manifest checksums before staged restore, restore
DB rows before plugin blobs, and prove the restored registry/capabilities and object reads against
the same manifest. A missing object, checksum mismatch, malformed config or partial plugin restore
must fail closed and leave the candidate quarantined. Do not read or record secret values; evidence
contains only presence, field names and masked effective values.

User-profile Google direct calls are a separate call-site lane, not an implicit exception to the
durable cap. Inventory profile enrichment/geocoding paths and route every billable request through
the same Nest reservation, ledger and admin-only visibility contract. Plugin routes receive an
additional security review: v4 registry and capabilities default-deny, actor and cross-trip
authorization is explicit, removed members and packing-private rows are denied, and
`safePluginId`, path traversal and managed permission-jail failures are fail-closed. Escaping or
unmanaged symlinks are rejected, while v4's explicitly configured in-root managed development-link
workflow is preserved and tested separately rather than disabled wholesale.

## Delegation contract

Subagents may use a lower model or lower reasoning effort only for a bounded lane with deterministic
inputs and commands. Every delegated prompt must include:

- exact branch/worktree and immutable base SHA;
- owned files and explicitly forbidden files;
- preservation matrix IDs and acceptance assertions;
- the single RED command expected to fail and why;
- the focused GREEN command and broader regression command;
- no commit/push/merge/deploy and no secret/production-data rules unless separately authorized;
- “not alone in the codebase; do not revert other edits”;
- handoff format: changed files, RED evidence, GREEN evidence, warnings, unresolved risks.

Workers never share the same owned file concurrently. A root integrator performs conflict resolution
and semantic reconciliation. Each lane receives a specification review followed by a code-quality
review; neither reviewer edits files. Completion is blocked while any preservation matrix HIGH item
is `pending`, `red`, `unverified` or `waived` without TOM's explicit decision.

## Gates

### Gate A — merge mechanics

- exact `33a33e7b` target revalidated;
- dry merge conflict manifest regenerated;
- actual merge has no unmerged entries;
- upstream-owned `migrations.ts` tree matches the pinned tag;
- no deleted legacy service was accidentally revived.

### Gate B — focused behavior

- DB matrix GREEN;
- auth/privacy, packing, Vacay and Google negative tests GREEN;
- map locale/Fold/calendar/SemVer/Android focused tests GREEN;
- public share note projection and non-disclosure tests GREEN.

### Gate C — repository quality

- shared/server/client/plugin-sdk build, typecheck, lint and coverage gates GREEN;
- strict i18n parity, page-pattern, GL split and theme gates GREEN;
- production build and Nest MCP load smoke GREEN;
- `git diff --check` and no generated drift.

### Gate D — release candidate

- immutable `4.1.1+jsnetworkcorp.<sha>` image and digest recorded;
- empty tmpfs bootstrap reaches schema 200 + fork IDs;
- sanitized current-fork backup migrate/replay/restore rehearsal GREEN;
- 390px, 1440px and Fold screenshots, anonymous public share, console/network evidence GREEN;
- Compose diff, mounts, plugin/storage restore and previous image documented.

### Gate E — external state

Origin push, fork `main` integration and production deployment are three separate explicit approval
gates. Passing A–D does not imply any of them.

## Rollback

Production rollback is an ordered operational procedure, not an image-only switch. First quiesce
application writes (including background jobs, plugin writes and uploads), then at the same logical
point take coordinated snapshots of the pre-migration DB, uploads/objects and plugin state. Verify
snapshot identities/checksums and the backup manifest before allowing migration. Run migration and
smoke checks while writes remain quiesced. Keep writes stopped throughout the rollback decision;
if rollback is selected, restore the pre-migration DB plus associated uploads/objects/plugins and
start the pinned old image. Once writes have resumed, pre-migration restore is forbidden: classify
the incident as reconciliation/forward recovery and use a new controlled procedure.

| Failure point                                              | Recovery                                                                                                                                       |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| before actual merge commit                                 | abort merge or discard isolated worktree                                                                                                       |
| after local integration commits, before DB rehearsal       | retain main untouched; reset only disposable branch by recreating worktree                                                                     |
| during sanitized rehearsal                                 | discard rehearsal copy; diagnose exact migration and marker                                                                                    |
| production preflight/migration/smoke while writes quiesced | keep writes stopped; choose forward recovery or restore the coordinated pre-migration DB/uploads/plugins snapshot, then start the pinned image |
| after writes resume                                        | prohibit pre-migration restore; freeze as needed and execute reconciliation/forward recovery with a new snapshot and evidence                  |
| after optional future S3 reassignment                      | use the separate object-storage rollback; DB restore alone is insufficient                                                                     |

No destructive reset, production restore or Compose change occurs under this design without TOM's
explicit target and approval.

## Residual decisions

The following defaults are selected unless TOM changes them before the relevant lane:

- Preserve the current Google durable hard-cap behavior; redesign its v4 call coverage before
  considering old batch enrichment UI retirement.
- Preserve packing Common-only template snapshots and instance scope until equivalent negative tests
  prove upstream behavior.
- Preserve all Vacay destructive-data guards; adapt them to v4 configurable leave-year semantics.
- Keep current storage assignment for the upgrade; do not couple S3 migration.
- Require storage/plugin manifest, checksum and staged restore rehearsal before any release
  candidate; an image rollback without those states is incomplete.
- Include user-profile direct Google calls and plugin capability/path-jail negative tests in the
  provider/security gates.
- Treat `places.notes` as trip-shared place notes, correct the misleading personal copy, and disclose
  that Map & Plan public links include them.
