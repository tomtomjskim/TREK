## Recommended execution order

1. Preserve the v4.1.1 checkpoint and its evidence as an intermediate local branch.
2. Create `sync/upstream-v4.2.0` in a separate worktree from that checkpoint and merge the exact
   peeled v4.2.0 commit without touching fork `main` or runtime.
3. Resolve migration/runtime conflicts before tests; resolve generated/repetitive locale and helper
   conflicts only after the semantic owners are fixed.
4. Run narrow RED/GREEN suites for DB 205, public Trip place notes, public Journey privacy/photos,
   packing privacy/totals, memory providers, CARTO fallback/offline prefetch, auth and PWA.
5. Run source/test typechecks, builds, full component coverage, server E2E and normal public/app
   Playwright. Keep clean-state documentation screenshot collection as a separately reported gate.
6. Re-run independent security/client/evidence reviews and bind every result to the final code SHA.
7. Only then decide whether a sanitized, offline/write-quiesced full-state restore rehearsal is
   justified. Main merge/push, image creation and production deployment remain NO-GO meanwhile.

## Decision boundary

Proceeding with an **isolated v4.2.0 incremental branch** is recommended because the v4.1.1 work
already supplies a reviewed merge base and the new delta is bounded. Automatic or direct main
absorption is not recommended: the 19 non-locale conflicts touch authorization, migration, privacy,
offline maps and public Journey output. Any unresolved HIGH preservation row, schema-205 replay
failure, anonymous DTO leakage, CARTO regression, or failed full code gate stops the integration.

Even after local code success, release remains NO-GO until the existing process-wide restore
quiesce/crash-recovery, encryption-key identity, sanitized rehearsal, immutable image and signed
device/browser artifact gaps are closed.
